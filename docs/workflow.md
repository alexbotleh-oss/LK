# Регламент работы с репозиторием

Версия: 1.0 · Дата: 2026-10-05 · Статус: действующий

## 1. Аудит

- Каждый аудит — отдельный commit с сообщением вида `audit: <название аудита>`.
- Отчёт аудита размещается в `reports/` (имя: `audit-<краткое-описание>-YYYY-MM-DD.md`).
- По итогам аудита ставится тег `audit-vX.Y.Z` на итоговый SHA коммита аудита.
- Тег считается созданным только после реального создания на стороне GitHub (или локальным Git с последующим push). Статус «тег не создан» фиксируется в отчёте честно, без подмены веткой или иными ссылками.

## 2. Исправление (patch)

Последовательность обязательна, пропуски не допускаются:

1. Ветка: `patch/<номер>-<краткое-описание>` (латиница, дефисы).
2. PRE-CHECK — фиксация исходного состояния перед изменением.
3. SNAPSHOT — сохранение копии изменяемых артефактов (файлы, состояние).
4. Внесение изменения.
5. Проверки: `pre_build_check.py`, `core_check.py` (и иные релевантные).
6. reverse-diff — сверка: только ожидаемые изменения попали в коммит.

## 3. Pull Request и merge

- PR создаётся из ветки `patch/...` в основную ветку.
- Описание PR: что изменено, какие проверки пройдены, ссылка на аудит.
- Merge выполняется только после успешного прохождения всех проверок.
- Merge из незавершённой цепочки шагов (2) запрещён.

## 4. Работа с основной веткой (main)

- Прямые push в `main` не используются. Все изменения — только через PR.
- Планируется: обязательный CI как условие merge (branch protection).
- Тег после merge ставится на SHA мержа в `main`, а не на SHA ветки `patch/...`.

## 5. Теги

- Допустимые способы создания тега: возможности, реально поддерживаемые GitHub-коннектором, либо локальный Git (`git tag` + `git push origin <tag>`).
- Обходные «манёвры» (подмена тега веткой, реф-манипуляции) запрещены.
- Если операция создания тега недоступна — статус фиксируется как «тег не создан, причина», повторная попытка не имитирует успех.

## 6. Правила агента

- Правила агента хранятся в `guards/rules/`.
- Изменения самих правил проходят тот же контроль: patch-ветка → проверки → PR → merge.
- Изменения правил агента не выполняются в обход регламента ни при каких условиях.

## 7. Сообщения коммитов

- Формат: `<тип>: <краткое описание>`.
- Типы: `audit`, `fix`, `docs`, `guard`, `refactor`, `ci`.
- Пример: `audit: сравнительный отчёт по протоколу защиты v1.7.7`.
